Architecture review

What package code belongs in Green, Red, and Blue?

Review of all six Package Skill repositories: once, airflow, walter, k3s, k8s, and clickhouse. The review covers exact duplication and broader reusable abstractions.

Executive conclusion

The strongest extractions are not package domain logic. They are the conventions every package rebuilds around the engines: stage-directory resolution, lifecycle preflight, conventional backend configuration, and provider-registry mechanics. Implement these behaviorally in all three SDKs, then migrate ONCE and Airflow first so the existing three-colour parity harness validates them. Migrate green-only packages afterward.

Do not move ONCE’s concrete cloud templates or provider catalog directly into the workflow engines. The mechanism is SDK-level; the concrete catalog is a separately versioned cloud/package concern. Moving provider HCL into Green/Red/Blue would make otherwise generic engines own a product policy and would not solve the current unsafe ONCE-internals dependency cleanly.

1. Add a canonical stage-directory resolver

Problem. Every package independently resolves <state-file-dir>/<workdir>/<profile>/<stage>. This is state-addressing behavior: a small drift can make colours render into different trees or point backend advice at a different directory.

Evidence: near-identical Green implementations in once/green/.../tools.clj:23, airflow/green/.../tools.clj:107, walter/.../tools.clj:48, k3s/.../tools.clj:24, k8s/.../utils.clj:8, and clickhouse/.../tools.clj:30. Equivalent copies exist at once/red/src/tools.ts:62, once/blue/.../tools.py:30, and Airflow Red/Blue.

Lift to: green.cli/stage-dir, red/cli.stageDir, blue.cli.stage_dir (or a small paths module in each SDK).

// Red API sketch
stageDir(opts, tool, { defaultWorkdir: ".colors", defaultProfile: "default" })

# Blue
stage_dir(opts, tool, default_workdir=".colors", default_profile="default")

;; Green
(cli/stage-dir opts tool {:default-workdir ".colors" :default-profile "default"})

Require an absolute engine state-file key when workdir is relative; preserve absolute workdirs. Packages then supply only their fallback profile, and backend and tool execution necessarily share one resolver.

2. Introduce a configurable lifecycle preflight step

Problem. Every workflow has a start-step that merges defaults, reapplies COLORS_PAR_*, distinguishes real execution from dry-run/build, aggregates environment/state/secret errors, enforces compute-prevent-destroy, and returns exit 2. Copies already differ in punctuation and whether environment guards are included.

Evidence: once/green/.../workflow.clj:66, airflow/green/.../workflow.clj:103, walter/.../workflow.clj:72, k3s/.../workflow.clj:23, k8s/.../workflow.clj:28, clickhouse/.../workflow.clj:17; matching ONCE/Airflow implementations in Red and Blue.

Lift to: a new SDK lifecycle module, parameterized by package callbacks rather than aware of compute, providers, or ONCE.

// Red API sketch
const start = lifecycle.preflight({
  defaults,
  envErrors: (env) => validate.envErrors(env),
  stateErrors: validate.stateErrors,
  secretErrors: validate.secretErrors,
  lifecycleEvents: ["create", "delete"],
  destroyGuard: { event: "delete", key: "compute-prevent-destroy" },
  afterValidate: async (opts, ctx) => ctx.real && ctx.event === "delete"
    ? adoptExistingState(opts) : withDeployKeys(opts, ctx.real),
});

The SDK should guarantee ordered error aggregation, exit 2, no secret validation for build/dry-run, and an injected environment for tests. Package-specific key generation/state adoption remains a callback.

3. Add “conventional backend” advice above existing backend primitives

Problem. The SDKs already expose local/S3/R2 advice and a selector, but each package rebuilds the same policy map and the same <profile>/<tool>.tfstate key.

Evidence: once/green/.../workflow.clj:143, airflow/green/.../workflow.clj:209, walter/.../workflow.clj:207, k3s/.../workflow.clj:66, k8s/.../workflow.clj:65, and clickhouse/.../workflow.clj:77. The same assembly appears in ONCE/Airflow Red and Blue. Existing lower-level hook: green/src/green/tofu.clj:160 and equivalents.

Lift to: tofu/conventional-backend-advice, retaining all low-level APIs.

conventionalBackendAdvice({
  dir: (opts) => stageDir(opts, tool),
  key: (opts) => `${opts.profile ?? fallback}/${tool}.tfstate`,
  choose: (opts) => opts["provider-backend"] ?? "local",
  fields: {
    s3: { bucket: "s3-bucket", region: "s3-region" },
    r2: { bucket: "r2-bucket", endpoint: "r2-endpoint" }
  }
})

Make key and directory functions explicit so Airflow can preserve delegated ONCE stage names. Do not silently standardize existing state addresses.

High valueModerate risk

4. Lift provider-registry mechanics, not provider data

Problem. All packages repeat entry, slot-keys, placeholder detection, missing-key discovery, selected-provider validation, secret-error formatting, tofu-env, and credential environment construction. Five packages import ONCE’s registry as an unprotected internal API; K8s copies a subset.

Evidence: clickhouse/.../validate.clj:25–31, k3s/.../validate.clj:11–31, k8s/.../validate.clj:36–44, airflow/green/.../validate.clj:69–112, and walter/.../validate.clj:69–96. Credential env is repeated in every tools namespace. ONCE has parallel implementations in all colours.

Lift to: green.providers, red/providers, and blue.providers, operating on caller-supplied registry data.

const selected = providers.select(registry, opts, slots);
providers.selectionErrors(registry, opts, slots);
providers.requiredErrors(registry, opts, slots, ownRequired);
providers.secretErrors(registry, opts, slots, ownSecrets, parName);
providers.toolEnv(registry, opts, [...slots, "provider-backend"]);
providers.refuseOverlay(env, "profile", "profile selects remote state");

Boundary: keep DigitalOcean/Hetzner/OCI/etc. definitions and HCL out of the SDK. A later colors-cloud package, implemented per colour or as language-neutral resources/data, should own the catalog. This removes the current “depend on ONCE internals” architecture without coupling the engines to ONCE.

Medium valueLow risk

5. Make SDK CLIs project-aware

Problem. Package CLIs repeatedly walk upward for colors.yml, detect explicit -f/--file, dispatch help and package events, and print outcomes. This exists both in package libraries and copied launchers.

Evidence: once/red/src/cli.ts:12–42, once/blue/.../cli.py:15–38, Airflow Red/Blue CLI files, and Green launchers in all six skills/package-*/ trees. Green SDK currently defaults only to green.yml; Red to red.yml; Blue to blue.yml.

Lift to: options on run-cli: defaultFile, searchParents, allowedEvents, and optional custom handlers.

runCli(workflow, args, {
  defaultFile: "colors.yml",
  searchParents: true,
  events: ["build", "create", "delete"],
  handlers: { describe: ({file}) => describeFile(file) }
})

Keep dependency bootstrap and contract checks in launchers: those must run before the SDK can be loaded. The SDK can eliminate post-bootstrap dispatch duplication, not bootstrap itself.

6. Let scaffolds write direct content

Problem. Every package ships a one-line raw template and wraps it with raw-spec solely to write generated JSON/YAML/key files. They also repeat the same alternate Selmer delimiters.

Evidence: ONCE tools.clj:14–55, Airflow tools.clj:97–149, Walter tools.clj:36–75, K3s tools.clj:20–43, K8s tools.clj:20–28, ClickHouse tools.clj:26–39, plus Red/Blue counterparts.

Lift to: a direct content spec accepted by scaffold, and an exported delimiter preset.

{ target: `${dir}/inventory.json`, content: inventory(data) }
// or scaffold.contentSpec(target, content)

scaffold.PRESERVE_JINJA_DELIMITERS

Delete the package raw resources after parity proves byte identity. Define deletion behavior exactly like template specs.

7. Add an interactive delegated-command runner

Problem. K3s and K8s contain almost identical implementations for POSIX shell quoting, inherited terminal execution, desired-state loading, environment validation, and subprocess-exit normalization for kubectl over SSH.

Evidence: k3s/.../kubectl.clj:13–58 and k8s/.../operator.clj:8–50.

Lift to: generic pieces only: process/run-inherit, process/posix-quote, and cli/run-delegated. Keep the remote kubectl argv and host alias package-specific. Port APIs to Red/Blue now for model parity even though current consumers are Green-only.

DeferExtract seam first

8. Consider a command-plan executor, not a GitHub domain module

ONCE and Airflow each model labeled gh commands, inject runners, execute sequentially, stop on create failure, tolerate delete absence, and clean ephemeral key state. A reusable process/run-plan could standardize this. However repository creation, environments, key publication, and seed pushes are product policy and should remain package code.

Evidence: once/*/github and airflow/*/github in all implemented colours.

Extract only after defining consistent semantics for “continue on delete”, stderr snippets, timeout, redaction, and cleanup. This is less urgent than findings 1–6.

Suggested implementation order

1 · Paths + scaffold content

Add parity tests in the three SDKs. Migrate ONCE first; run all SDK suites and ONCE parity.

2 · Backend convention

Build above existing primitives. Assert generated backend.tf.json and state keys are unchanged byte-for-byte.

3 · Provider mechanics

Add caller-supplied registry helpers. Migrate ONCE and Airflow in one parity-protected change, then Green-only packages.

4 · Lifecycle preflight

Lock error ordering and exact messages first. Use callbacks for package state adoption/key generation.

5 · CLI options

Move upward discovery and event dispatch after bootstrap. Preserve script-adjacent fallback behavior in launchers.

6 · Optional seams

Add interactive process and command-plan helpers only with focused tests and at least two migrated consumers.

Verification gates

  • SDKs: green: bb test + clojure -X:test; red: bun test + bun run typecheck; blue: uv run pytest.
  • Three-colour consumers: ONCE and Airflow per-colour suites plus both parity and launcher scripts.
  • Green-only consumers: unit tests, golden diffs reviewed rather than blindly accepted, and launcher scripts.
  • State safety: assert every existing stage directory and <profile>/<stage>.tfstate key remains unchanged.
  • Secrets: assert generated trees contain lookups, never credential values; build and dry-run remain credential-free.
